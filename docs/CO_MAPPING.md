### Key Viva Questions & Explanations

#### 1. Why use a Doubly Linked List for the Timeline instead of an Array?
*Answer:* A case timeline frequently has newly discovered events inserted chronologically between existing events as an investigation unfolds. A Doubly Linked List supports $O(1)$ node insertion and deletion once the adjacent node is known, without shifting elements like an array ($O(n)$). Furthermore, physical bidirectional navigation (moving back and forth between previous and next events) is handled natively by `prev` and `next` pointers.

#### 2. Why does Binary Search require an indexed array snapshot rather than running directly on the Linked List?
*Answer:* Binary Search fundamentally relies on $O(1)$ random access to calculate and inspect the midpoint: `mid = (low + high) // 2`. In a linked list, reaching the middle node requires sequential pointer traversal ($O(n)$), which destroys the $O(\log n)$ time complexity. Thus, the application maintains a Doubly Linked List for step navigation and creates a sorted indexed array snapshot when running binary search.

#### 3. How does Separate Chaining resolve hash collisions?
*Answer:* Each bucket in our hash table holds a linked list / collection of entries that mapped to the same hash index (`hash(key) % capacity`). When two distinct keys (e.g. `CLUE-1` and `CLUE-4`) yield the same bucket index, the second entry is appended to that bucket's chain. Search scans only the entries within that specific bucket rather than the entire table.

#### 4. Why does BFS guarantee the shortest path in unweighted graphs while DFS does not?
*Answer:* BFS explores graph vertices level by level (expanding all vertices at distance $k$ before vertices at distance $k+1$). Consequently, the first time BFS reaches the target destination node, it is mathematically guaranteed to have taken the minimum possible number of edges. DFS explores one branch as deeply as possible before backtracking, which may discover an unnecessarily convoluted, long path.
